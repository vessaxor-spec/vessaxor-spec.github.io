TECHNICAL NOTES

Persistent systems · Governed orchestration · Verifiable execution

Architecture above models, in plain technical language.

These notes explain the design problem behind VESSAXOR, TEO, and GroX without requiring repository context first: how AI systems can keep authority, evidence, state, verification, and recovery stable while the models inside them change.

01 / PERSISTENT AI SYSTEMS

A persistent AI system is more than a model session.

A model can reason or generate output, but persistence belongs to the surrounding system: durable state, explicit authority, provenance, recovery rules, evidence, and a way to resume work without pretending a new session is the same execution context.

PLAIN MEANING

Keep the operating rules when the intelligence changes.

The system should be able to replace or upgrade a model without silently changing who may act, what state survives, how results are verified, or what happens after failure.

VESSAXOR DISCIPLINE

Authority · Evidence · Continuity.

These are treated as architecture concerns rather than model features. They are visible across both flagship systems even though TEO and GroX solve different problems.

02 / GOVERNED AI ORCHESTRATION

Routing should resolve responsibility before choosing a model.

TEO is a vendor-neutral orchestration specification and runnable reference control plane. Its public control path separates responsibility, required capability, eligible implementation, and verification instead of treating provider selection as the first architectural decision.

  1. 01ResponsibilityWho is accountable for the work?
  2. 02CapabilityWhat does the work actually require?
  3. 03ImplementationWhich eligible route may perform it?
  4. 04VerificationWhat evidence must exist before completion?

03 / BOUNDED AI EXECUTION

Intent becomes durable action through an explicit command spine.

GroX is a persistent AI command environment. Commander intent becomes a bounded Mission through one operational orchestrator, explicit Mission scope, Crew execution, attributable evidence, independent verification, durable state, and recovery controls.

04 / EVIDENCE-BEARING EXECUTION

A plausible result is not the same as a verified result.

VESSAXOR uses a public claim-to-evidence pattern so important statements can be inspected rather than merely asserted. The pattern is intentionally narrow: claim, evidence, boundary, primary source.

CLAIM

State what the system is said to do.

Keep the claim specific enough that evidence could disprove or qualify it.

EVIDENCE

Point to the artifact, test, run, or control.

Evidence should correspond to the claim actually being made.

BOUNDARY

State what the evidence does not prove.

Lab evidence, reference behavior, staged capability, and production behavior are not interchangeable states.

PRIMARY SOURCE

Keep the repository authoritative.

The portfolio explains and exposes evidence; it does not become a parallel source of system truth.

05 / BOUNDARIES

What these notes are not claiming.

They do not claim that model capability creates authority, that a passing test proves every deployment environment, that reference implementation equals unrestricted live execution, or that persistence makes a system autonomous beyond its explicit command boundaries.

DESIGN RULE

Capability does not grant permission.

More capable models can expand implementation options, but authority remains a separate system decision.

EVIDENCE RULE

Implementation is not completion.

Consequential work needs checks, evidence, verification, and an explicit operating state before it should be represented as complete.
