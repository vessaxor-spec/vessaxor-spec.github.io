GroX / PERSISTENT VESSEL

v0.7.1 APEX QUALIFIED

How does intent become durable action?

GroX keeps one command spine while Missions, Crew, capabilities, evidence, verification, persistence, and recovery remain bounded beneath Commander intent.

01 / DEFINITION

A persistent command environment, not a long-running chat.

The public layer explains the Vessel in plain language while preserving GroX-native command and authority terms.

PLAIN LANGUAGE

GroX turns human intent into governed work that can survive interruption.

It creates Missions, assigns eligible Crew under bounded Mission Orders, records evidence, requires independent verification where policy says so, and preserves state needed for recovery.

EXACT SYSTEM CLAIM

Commander → Pilot GorXu → Divisions → Standing Crew.

The Commander retains ultimate authority. Pilot GorXu is the sole operational orchestrator. Capabilities, tools, schedulers, memory, evaluators, and external systems are resources, not parallel command layers.

02 / COMMAND PATH

One orchestrator. Bounded execution.

Failure, fallback, and recovery may restore reversible execution but may not widen authority or silently rewrite Commander intent.

GroX / CANONICAL FLOW

Commander intent → verified Mission outcome

Mission Control is GroX-native policy and advisory support used by GorXu when required. It is not a parallel command layer.

03 / CLAIM → EVIDENCE

Persistence and recovery are explicit surfaces.

GroX exposes bounded inspection, Mission execution, and reconstitution paths rather than treating continuity as an assumption about a surviving process.

CLAIM

Bounded Missions are runnable.

The public CLI can run an inspect-mode Mission without turning inspection into Repair authority.
